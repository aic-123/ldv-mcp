## §1 方向 C 是什么

    seq(x)        = 从 x 出发的**确定性链**（沿 relations，每步取 id 最小的未访问后继）
    方向 payload  = 一组**前缀**（前缀语言，`frozenset[tuple]`）
    x 属于 d      ⟺ 存在 p ∈ payload 使 p 是 `seq(x)` 的前缀
    合并 = 并    代价 = 前缀距离（要砍几个符号）    命中 = 前缀匹配

### 与 A / B 的差异（C0 §2 那张表的实测版）

| 轴 | A 键集包含 | B 锚点可达 | **C 序列前缀** |
|---|---|---|---|
| payload 是什么 | (require, forbid) 两个键集 | 一组锚点 | **一组前缀** |
| **有序吗** | 无序 | 无序 | **有序** ← 前两个压不到 |
| 合并 | 分量取**交** | 取**并** | 取**并** |
| 代价 | 计数（丢几条要求） | 图距离（走几步） | **前缀距离**（砍几个符号） |
| 代价量纲 | 非负整数 | 非负实数 | 非负整数 |
| 「否」的依据 | **证明**（键包含矛盾） | **遍历**（可达闭包不交） | **算覆盖集合** |
| 第三态来源 | 分辨率（`rank < min_rank`） | 分辨率 + 拒绝遍历 | 分辨率 |
| 需要世界吗 | 不需要（只看节点自己） | 需要（整张图） | 不需要（`seq` 已把世界编进 payload） |

## §2 它压出来的三个问题，逐条判定

### 2.1 §I4 的「两个」是 B-tree 的遗产 —— **能装下，代价可量**

有序方向的自然细化是 **trie**：一个节点按「下一个符号」分出 **k** 个子方向。
§I4 硬编码 `→ 两个方向`，所以 C 只能把 k 个符号**二分**（大桶先放、进当前较小的那堆）。

**能装下**（实测 37 个方向、最大秩 8，与 A 的 39/8 相当），
**但形状不自然**，而且代价量得出来：

    空权威层（§K2 创建后标记失效的方向）    A 14/39（36%）   B 0/71（0%）   C 16/37（43%）

同一套 §K2、同一个内核，**形状越自然，空层越少**。B 的合并就是取并、切分点随手可得，
一个空层都没有；C 被迫二分，切出 43% 的空层。

**判定：不算押错。** §9 的判据只有两个症状 —— 必须新增方法、必须把方法拆开。
这里两个都没有：`劈开` 仍然是**一个**方法、仍然只有**两个**返回值。
代价是**多花层数**（性能），不是**装不下**（能力）。
⇒ 记一条文档说明即可，接口不动。

### 2.2 §I2 的细化定义是错的 —— **但三个方向都错，不是 C 压出来的**

设计文档 §3 与 `core/interfaces.py` 都写过：

    细 ⊑ 粗   ⟺   合并({细}) = 粗

**实测：这条对三个方向都不成立。**

    A keyset     39/39 个方向满足 合并(单元素) == 自身
    B reach      71/71 个方向满足 合并(单元素) == 自身
    C sequence   37/37 个方向满足 合并(单元素) == 自身

因为**合并(单元素) 是恒等**（合并一个方向只能得到它自己），
于是 `合并({细}) = 粗` 对**任何严格细化**都要求 `细 = 粗` —— 自相矛盾。

⇒ 这不是接口被压垮，是**文档写错了**。C 的作用只是让它**变得显眼**：
C 有 `('概念',) ⊐ ('概念','案例')` 这种「加一个符号」的细化，
而「细化由加符号产生、不由合并产生」在 C 上一眼可见；
在 A / B 上两种读法**碰巧分不出来**（它们的细化恰好也能写成某种集合运算），
所以那个错一直没被看见。

**正确的写法**（已落进设计文档 §I2 与 `interfaces.py`）：

    §I2 的「更粗」= **行为上的覆盖**：细方向收下的，粗方向不许拒。
    §1 的「细方向包含于粗方向」分两层，**只有一层是硬要求**：

        成员层      members(子) ⊆ members(父)          ← 硬要求（这是「分辨率」）
        过滤器层    覆盖(子) ⊆ 覆盖(父)                ← **不是**硬要求
        健全性      members(d) ⊆ 覆盖(d)               ← 硬要求（这是 §K8 那一半）

    过滤器只要**健全**（覆盖得住自己的成员）就够，不需要层层嵌套。

### 2.3 §I3 容纳第三种代价语义 —— **成立**

    A 计数（非负整数）   B 图距离（非负实数）   C 前缀距离（序列对齐）

§I3 只要求「同层内两两可比」，没有要求统一量纲、没有要求归一化。
实测 C 的 1296 个代价值全部可比，**内核一个数没动**。

⇒ C5 §3.1 说 §I3「同时容纳两种毫不相干的代价语义」，现在是**三种**。

## §3 这一轮实测的新发现

### 3.1 E1 —— §1 的「细方向包含于粗方向」只有一半成立，而原因是 D1

按 §2.2 的分层，实测过滤器层的包含：

    覆盖(子) ⊆ 覆盖(父)      A keyset   16/24 成立（8 处不成立）
                            B reach    70/70 成立
                            C sequence 20/20 成立

**A 有 8 处不成立。** 看具体例子：子 D4 的覆盖**比父 D2 大**（多收下 judge-000x）。
根因在 `KeysetPlugin.split`：

    common = 所有成员的键的交集
    return ((common | {best}, ∅), (common, {best}))      ← 两个子方向**从 common 重建**
                                                            而不是从**父的 payload** 细化

**为什么它没法从父的 payload 细化**：`§I4 劈开` 的入参是「**一组项**」（C5 的 D1），
插件**看不到父方向**，手上只有项。所以它只能从项里**重新猜**父的意图，
猜出来的东西**不保证**是父的细化。

⇒ **D1 不是免费的。** 把入参从「一组方向」改成「一组项」修好了「首次展开时子方向还不存在」，
但同时也**拿走了插件细化父方向的能力**。

**这不是违规**（下面 3.3 会说明健全性靠什么守），所以不改接口。但它说明：
`§I4` 的签名还有第二种取法 —— `劈开(父方向, 一组项) → 两个方向`。
**留白，不在这一步动**（见 §6）。

### 3.2 E2 —— B15 的机制我写错过一次，而且它在退化结构上会空转

`B15`（结构可复现：换插入顺序 ⇒ 树同构）原来的 docstring 写：

> 内核之所以可复现，靠的是**建根时就把全部项装进去**（`build()` 里 …）

**实测不成立。** 真正守住顺序无关的是：

    `expand(d)` 劈的是 `d` 的**全部成员**，而 `d` 的成员由父的劈法决定
    ⇒ 「成员集合 = 全集的一个确定函数」这条性质**逐层归纳**地传下去

「建根时预装」只是这条归纳的**基例**。三种改法实测对照：

| 改法 | 结果 | B15 |
|---|---|---|
| 去掉 `build()` 的预装 | 根变叶，**整棵树退化成一个方向** | 仍是「过」← **空转** |
| `expand()` 劈之前不给成员排序 | 同集合迭代序一致，看不出差别 | 仍是「过」 |
| 方向攒够容量才劈（B-tree 上溢分裂） | **真的顺序相关**（13/15/13） | **红** |

**两个后果，都处理了**：

1. **机制说明改对了**（写进 `checks/structure.py`）。
2. **补了一道非退化前提**：指纹少于一层分裂 ⇒ 报**「未展开」，不报「过」**。
   原来它会在「根就是叶」的树上报「3 种插入顺序得到同一结构」——
   **同构于「什么都没有」**，正是「空转与通过长得一模一样」。
3. **补了注入**：`_SplitOnOverflow`（`tests/test_injections.py`）。
   在此之前 `B15` 是一句**没有注入验证的声称**。

### 3.3 E3 —— `B1` 依赖查询集 ⇒ 补了 `B16`

`B1`（假阴禁止）是拿**查询集**的 ground truth 去比的。于是：

    同一个「插入时选代价最大的子方向」的坏内核（102 个成员落在自己方向的覆盖外）
      B1 在 40 条查询下   判「否」   ← 查到了
      B1 在  3 条查询下   判「是」   ← **绿了**
      B1 在  0 条查询下   判「未展开」 ← 跳过（至少没有假装通过）

**查询集一换，`B1` 就可能瞎。** 所以补了 `B16`：

    B16  过滤器健全：  members(d) ⊆ { x : 代价(d, x) = 0 }     ← 不看查询集，一次全查

实测三个方向 **159 / 224 / 192 个成员，全部落在自己方向的覆盖里，0 例外**。
它不是「新发现了一个 bug」，而是把 `B1` 依赖查询集的那一半**补成与查询集无关**：

    B1   管「插件**说**得准不准」（行为式，靠查询集）
    B16  管「内核**分**得对不对」（结构式，靠代价）

顺带，这一条也解释了 **A 的 8 处「过滤器不嵌套」为什么无害**：
健全性（`B16`）成立 ⇒ `命中` 说「否」的证明覆盖得住自己的全部成员 ⇒
剪枝安全。**过滤器不需要嵌套，只需要健全。**

### 3.4 三个方向的「代价形状」不一样（度量，不是判据）

| | 假阳率 | 空权威层 | 方向数 | 事件数 |
|---|---|---|---|---|
| A | **56.7%**（粗过滤器，问得快） | 36% | 39 | 74 |
| B | 29.0% | **0%** | **71**（最多） | 115 |
| C | **0.0%**（每次都要算覆盖） | 43% | 37 | 72 |

三种权衡，三种形状，接口都没拦。**这三列都不进退出码** —— 它们度量的是
「好不好用」，不是「违不违规」（继承 dce 的 `report()` 纪律）。

## §6 留白（明确**没做**的）

按 C5 §8 的顺序，第三个方向排在最前，因为它**可能推翻接口**。现在复核完了 ——
接口站得住。剩下的按「会不会改接口」分两类：

**不改接口（工程）**

1. 持久化 / 并发 —— 内核 `Ledger` 已经是 append-only，落盘是纯工程。
2. 层数策略 —— R2 已定「不设全局上限，由插件决定何时分不开」。
3. 曝光模型标定 —— R1 已定按位次 + 下界，标定要真实使用数据。

**可能改接口（所以留白，不擅自做）**

4. **`§I4` 是否要带上父方向**（E1）。
   `劈开(父方向, 一组项) → 两个方向` 能让 A 的过滤器真正嵌套，假阳率大概率下降。
   但这要动**已验证的签名**，而且**不是必须**（健全性已由 `B16` 守住）。
   ⇒ 留给下一步拍板。
5. **`§I4` 的返回值是否该是 k 个**（§2.1）。
   改成「一组方向」能让 C 少花层数（43% 空层大概率下降）。
   同样：**能装下就不算押错**，动它要付重新验证的代价。
   ⇒ 留给下一步拍板。

**这两条都指向同一个判断**：`§I4` 是七个位置里**最像 B-tree 遗产**的一个。
它「能装下」三个差异极大的方向，但每次都要多花点东西
（A 花假阳率、C 花层数）。**装得下 ≠ 装得好** —— 这句话本身是这一轮的结论。
