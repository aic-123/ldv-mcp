## 一、功能矩阵（改形状之后，每件能力还在不在）

| 能力 | 旧路径 | 现在的路径 | 判据 |
|---|---|---|---|
| 按维度查 | `ask(require)` | 同（默认给正文） | S4 / S5 |

| **只看某一支** | `read(did=)` | 拿该支的 `must`/`mustnot` **再问一次** | **S29** |

## 二、指标名不自己发明（RAGAS 的检索侧）

RAGAS 把指标分两半：**检索侧**（context precision / context recall）与**生成侧**
（faithfulness / answer relevancy）。本产品是**检索器，不生成文本** ⇒ 只对得上前一半。

| 指标 | RAGAS 的定义 | 本仓库的读数 |
|---|---|---|
| **context_recall** | 取回里是否含回答所需的信息 | 针的位置扫描 3/3（三处位置全中） |
| **context_precision** | 取回的条目里的信噪比 | 1.00（67/67 与问题同项目） |
| faithfulness | 答案有没有编 | **不声称** —— 插件不生成文本 |
| answer_relevancy | 答案是否切题 | **不声称** —— 同上 |

⚠️ 生成侧那两个指标属于 **agent**，不属于插件。插件能保证的是「给到的东西逐字来自语料」，
不是「agent 用得对」。混在一起报，就是把别人的责任算成自己的。

## 三、长上下文那套方法：哪些能用、哪些用不了

| 方法 | 出处 | 本装置能不能用 |
|---|---|---|
| **Lost-in-the-Middle**（位置偏差：两端好、中间差） | Liu et al. | **用不了**：那是**模型**的性质。本装置里的「无插件侧」是字符串查找，天然与位置无关 |
| **Context Rot**（输入越长性能越降） | Chroma 2025-07 技术报告 | **用不了**：同上，需要真模型 |
| **NIAH 单针** | 经典做法 | 能用但**不够**（见下） |
| **RULER 的多针** | RULER 对单针的批评 | **能用，已加**：同项目的两针题 |
| **位置扫描（不是只放一个位置）** | NIAH 的标准批评 | **改造成能测的**：扫**语料内**位置（第 1 条 / 中间 / 最后一条） |
| **重复 n 次取均值 ± 标准差** | 通用实验规范 | **能用，已加** |

### 那本装置实际测出了什么

```
① 语料内位置扫描（针放在语料第 1 条 / 中间 / 最后一条）
   第 1 条   3/3   precision 1.00   取回 67 条
   中间      3/3   precision 1.00   取回 67 条
   最后一条   3/3   precision 1.00   取回 67 条
   ⇒ 命中率不随针在语料里的位置变化 —— 划分结构**没有位置偏差**
     （这是对 Lost-in-the-Middle 的对照：偏差在长上下文里存在，在这里不该存在）

② 多针（RULER 的批评）
   同项目两针都在取回里：True
   跨项目的那条不在：False（**这条本来就不该在**，是对照）
   ⇒ 单针探针会把「只找到一条」当成「找到了」

③ 重复 3 次
   每次 5790 tokens｜5790 ± 0（0.0%）
   ⇒ 检索成本是**确定性**的（不同于生成），所以单次读数可以当准数用 ——
     但这一条是**证明**出来的，不是假设
```

### ⚠️ 口径修正（外部评审 A3，2026-10-25）：分母曾经在重复计数

|---|---|---|
| 小规模 | 139 vs 135「省」 | **228 vs 135（贵 1.69×）** |
| 大规模 | 35 vs 134「省 74%」 | **61 vs 134（省 2.2×）** |

⚠️ **2026-10-26 又涨了一次，原因是「把元数据读出来」**：
`orient.derived_meta` + `ask.derived_provenance`（判据 `S44a–c`）让

这是**修对的代价**：`derive` 一直强制要求 `derived_from`，而它写进去后没人读 ——

## 六、另一族方法：蜕变测试（不判「对不对」，判「该怎么变」）

例子驱动的测试（S1–S35）回答「这个输入下输出是什么」。但检索系统最要紧的是**关系**：
加一条会怎样、删一条会怎样、换个键序会不会变。这些「预期值」写不出来（语料一换就全变），
**但关系是稳定的** —— 这正是蜕变测试（Metamorphic Testing, Chen 1998）解决的问题：
**测试准则问题**（oracle problem）。

`probes/metamorphic.py` 八条关系：

| MR | 关系 | 违反了说明什么 |
|---|---|---|
| MR1 | 键序无关：`[a,b]` 与 `[b,a]` 答案集相同 | 把 require 当成有序结构 |
| MR2 | 加**不满足**约束的项 ⇒ 答案不变 | 谓词过宽 |
| MR3 | 加**满足**约束的项 ⇒ 恰好 +1 | 插入漏 / 键没生效 |
| MR4 | 多加一个键 ⇒ **严格**变小 | 交集算错（越加越大） |
| MR5 | 只改正文 ⇒ 答案不变 | 结构偷偷依赖了 body |
| MR6 | 重命名文件 ⇒ 答案不变 | 拿文件名当 id |
| MR7 | 加派生维度 ⇒ 无关查询不变 | 派生维度污染 |
| MR8 | 删一条 ⇒ 恰好 −1 | 删不干净（幽灵成员） |

实测全过。其中 **MR4 第一版是空转**（`type=立场 + source.kind=论文` ⇒ 3 vs 3，
「子集」恒真）—— 换成 `概念 8 → 教材 3` 并断言**严格**变小，才是真测。

⚠️ **一条已知的未做**：这八条「会不会红」**没有用故障注入验证过**。
    按本仓库的纪律（反向对照必须回退**真源码**），那要单独做一次注入；
    这一轮只证明了「当前实现满足这八条关系」，没证明「违反时它抓得住」。

### 读数

```
① 位置扫描（12 条，2 次/档）
   头 2/2｜中 2/2｜尾 2/2        ⇒ 这个长度上**没有位置偏差**

② 编造率（faithfulness 的下界近似）
   答案「指标 7.77，batch=64」｜答案里的数字全在上下文里 ⇒ 编造 0
   成本：33,382 tokens / **25 次调用**（均值 1335/次）
   ⚠️ 这个调用数一度印成 7 次（次数是写死的 REPEATS*3+1，加了长度扫描没跟着改）
   ⇒ 读数里的计数必须**数出来**，不能写死

③ 长度扫描（12 / 60 / 200 条 × 头/中/尾，2 次/档）
     12 条（~144 tok）   2/2  2/2  2/2
     60 条（~720 tok）   2/2  2/2  2/2
    200 条（~2400 tok）  2/2  2/2  2/2     ⇒ **2400 tokens 以内测不到退化**
```

### 结论（负结果也是结论）

**deepseek-chat 在 2400 tokens 以内没有位置偏差、没有漏针。** 这不是失败：
- 经典 context rot / Lost-in-the-Middle 要**上万 token** 才显形；
- 也就是说，**在「12–200 条笔记」这个量级上，靠上下文装得下且不漏**；
- 所以插件在这个量级的价值**不是「不漏」**（模型也不漏），而是
  **跨会话 + 超出窗口之后仍可查**（那一条在 `repeat_cost.py` 里量过）。

⇒ **已做（同日 §8，`probes/real_scale.py`）：拉到 67k tokens，单针任务仍然不漏。**
所以现在能说的是「**在 8k–67k tokens 的单针任务上测不到退化**」，
不是「拉到 1 万就会退化」。要再往上只能换更难的题（多针 / 多跳），不是加长。

## 八、长上下文 × 三种给法（有对照的版本）

上一轮的读数**没有基数**，只有「无插件侧」一个数 ⇒ 拉长上下文也没意义。
`probes/real_scale.py` 加对照：**同一批笔记、同一个问题**，三种给法，token 用 **API 回传的真实用量**。

```
── 500 条笔记（~8k tokens）──
   WITHOUT 全塞 prompt    中   8069 tokens
   WITH 窄查询（唯一键）    中     62 tokens
   WITH 宽 limit=50       漏    843 tokens（取回 50 条）

── 2000 条（~33k）──       WITHOUT 33170 中｜窄 62 中｜宽 843 漏
── 4000 条（~67k）──       WITHOUT 67170 中｜窄 62 中｜宽 843 漏
```

### 三条结论（都对插件不利或中性，但它是真的）

1. **长上下文本身兜得住这个量级**：67k tokens 内 deepseek-chat 单针任务**不漏**
   ⇒ 在「几百到几千条笔记」这个量级上，**「不漏」不是插件的卖点**。
2. **插件的优势是成本**：窄查询 **62 tokens vs 67,170 tokens = 1/1083**，
   而且是**跨会话**的（`repeat_cost.py` 量过：会话内重复上下文赢，历史/跨会话插件唯一能做）。
3. ~~**宽查询 + 小 limit 会漏**~~ ⇒ **这一条是探针设计的问题，不是产品缺陷**
   （2026-10-24 用户指出）。真实使用中，查询覆盖不上时 agent 会去**要方向 / 要节点**
   （`derive` 一个维度，或走 `out_of_structure` → `can_agent_fill` 那条路），
   不会拿一个覆盖不到的查询硬问。我把针放在查询够不着的位置，当然取不回 ——
   那是**我制造的覆盖缺口**，然后当成产品的漏记了一笔。

   保留下来的真问题是另一个：**limit 卡住时不许当成「不存在」**。
   现在 `ask` 在 `n_answer > limit` 时明说「只给了前 M 条，还有 K 条没给，
   要更多就放大 limit，别拿没给的当不存在」（判据 S31 守着）。

⇒ 一句话：**插件不是「更强的检索」，是「便宜 3 个数量级 + 跨会话」的检索。**

## 九、不声称的三件事

1. **不测模型行为**（会不会编、位置偏差、context rot）—— 那要接真模型。
   本装置测的是**检索侧**，这一条写在这里，免得读数被读成「模型评测」。
2. **不声称 faithfulness / answer_relevancy** —— 生成侧属于 agent。
3. **不把不同单位的数加起来**（每问 / 每条 / 一次性），那是最容易造出来的假结论。
