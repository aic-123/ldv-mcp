# 长场景实测：空库起，14 天，六类问题

> 2026-10-24 ｜ 探针 `probes/long_scenario.py` ｜ 逐字输出 `probes/out/long_scenario.out.txt`

## 这个实验想回答什么

不是「模型会不会编」（那要真模型），是三个能测的：

1. **同一批数值事实，在「窗口 + 压缩」下还能命中多少** —— 答案偏移的真实形态
2. **插件要花多少上下文** —— 每次查询吐多少字
3. **长流程里撞到缺口，agent 补得上吗** —— 且**不打断用户**

## 对照怎么做的（第二版，第一版不公平）

| | 条件 |
|---|---|
| **WITH** | 插件：笔记进 store，问题走 `ask`（按需取回，与笔记总量无关） |
| **WITHOUT** | **窗口 12 条 + 压缩**：写满就把最老的 3 条压成一句摘要 |

⚠️ **第一版把 WITHOUT 做成「FIFO 硬掉出」，那是不公平的** —— 真 agent 会压缩。
压缩的真实后果不是「什么都忘了」，是「**主题还在，数值没了**」。

事实由固定种子运行时生成（`lr=3.17e-6`、`尖峰 2.73`），不在任何训练数据里。

## 结果

### ① 空库能起来了（**0 项，不写占位文件**）

```
空库 orient ⇒ 0 项（0 = 空库，不写占位文件）｜键 0 个
```

空库就是空库：`ask` 回 `n_answer=0` / `stopped=empty`，**不往用户目录里塞任何占位文件**。
⚠️ 2026-10-24 曾用一条 `_keystone.md` 占位（当时内核把空目录当「找不到语料」），
2026-10-25 起内核直接接受空语料 ⇒ 那个机制已删。
「目录不存在」仍然报错（`find_corpus` 用 `is_dir()` 判）—— 空库与路径写错**分得开**。

### ② 缺口不打断用户，agent 自己补

```
ask require=[project=alpha] ⇒ ok=False｜can_agent_fill=True
next_step=['derive 一个维度（把这类取值建成可查的轴，带理由与来源）',
           '或映射到 vocabulary 里已有的键（换个问法）']
⇒ 无此键 → can_agent_fill → derive project（2 项）→ 再查 ok=True（2 项）
```

原因：**自定义字段只进「字段名」键，不进「字段=值」键**（内核只给 `type` /
`evidence_status` / `source.kind` 这类枚举字段生成值键）。
用户看不到「拒收」这种消息 —— 它只出现在 agent 那一侧，附带「你能怎么补」。

### ③ 答案偏移（核心读数，阶跃而不是渐变）

```
检查点        d01.lr      d02.base    d03.不可复现    窗口字数
第  3 天      有/有        有/有        有/有          115
第  6 天      有/有        有/有        有/有          216
第  9 天      有/有        有/有        有/有          299
第 12 天      有/有        有/有        有/有          380
第 14 天      有/无        有/无        无/无          367   ← 第 13 天压缩
```

（`有/无` = WITH 有 / WITHOUT 无）

- **WITH 全程 5/5 保持**
- **WITHOUT 到第 13 天压缩时，三条数值一起没** —— 是**阶跃**，不是渐变
- ⚠️ 偏移的表现是**沉默**（答不出来），不是错误。沉默比错误更难发现。

### ④ 主题题：WITHOUT 不输（这才是公平的分界）

```
WITH    ⇒ 14 条都有 project 字段，查得到
WITHOUT ⇒ 压缩摘要里项目名还在：True
          （摘要：【摘要】早前 3 条笔记（项目：alpha/beta/gamma），…）
```

⇒ **压缩丢的是精度，不是话题。** 所以「插件 vs 压缩」的真实差别是：

| 问题类型 | 压缩后的上下文 | 插件 |
|---|---|---|
| 数值（lr 多少、baseline 多少） | **输** | 有 |
| 主题（覆盖哪些项目） | 不输 | 有 |
| 结构（beta 几条） | 输（要数全量） | 有 |
| 追述（第 3 天那条） | 输（细节没了） | 有 |

### ⑤ 全量重建是设计，不是补丁

```
全量重建派生维度：第 2 天 3 项 → 现在 14 项
覆盖率 {'covered': 14, 'uncovered': 0, 'note': '全部节点都有值'}
```

派生维度是**快照**（建完之后新写入的节点不在里面），所以**全量重建是常规动作**，
`coverage` 只负责告诉你「该重建了」。
（`uncovered` 现在是 0 —— 删掉基石之后，语料里每一项都是用户真写的，都能覆盖到。）

## token 成本（真 tokenizer，`cl100k_base`）

> 探针 `probes/token_cost.py` ｜ 逐字输出 `probes/out/token_cost.out.txt`
> ⚠️ `cl100k` 不是 DeepSeek 的 tokenizer，绝对值有偏差；两边**同口径**，比的是比例。

### 小规模（14 条笔记，窗口 12 条）

```
窗口常驻 398 tokens（每问都要付一遍）
一次性成本（读全库 + derive project）：2959 tokens
问题                   WITH  WITHOUT    答案项   结论
窄：alpha 的坑            560      405      1   插件贵（1.38×）
中：beta 全部            1501      404      5   插件贵（3.72×）
宽：所有实验               1071      404      3   插件贵（2.65×）
元：整个库                3758      403     14   插件贵（9.33×）
⇒ 4 问累计：WITH 6890 vs WITHOUT 1616（4.26×）
⇒ 每条答案的 token：WITH 300（23 项）vs WITHOUT 135（只能看见 12 条）
```

### 大规模（140 条笔记，窗口 12 条）

```
窗口常驻 396 tokens（每问都要付一遍）
一次性成本（读全库 + derive project）：21924 tokens
问题                   WITH  WITHOUT    答案项   结论
窄：alpha 的坑           1375      403     12   插件贵（3.41×）
中：beta 全部            3308      402     47   插件贵（8.23×）
宽：所有实验               4048      402     35   插件贵（10.07×）
元：整个库               10494      401    140   插件贵（26.17×）
⇒ 4 问累计：WITH 19225 vs WITHOUT 1608（11.96×）
⇒ 每条答案的 token：WITH 82（234 项）vs WITHOUT 134（只能看见 12 条）
```

### 怎么读这两个数（这条最要紧）

**按「每问」算，插件在所有情况下都更贵**（1.38× ~ 26×）。但这个比较是**拿「答不了」当「便宜」**：
WITHOUT 只带 12 条，问 140 条库的事它根本答不全 —— 便宜是因为它无知。

**可比的单位是「每条答案」**：

| 规模 | WITH（每条答案） | WITHOUT（每条答案） | 谁便宜 |
|---|---|---|---|
| 14 条（≈窗口容量） | 300 tokens | 135 tokens | **插件贵**（固定开销摊不开） |
| 140 条（≫窗口） | **82 tokens** | 134 tokens | **插件便宜 39%** |

⇒ **交叉点在「库 ≫ 窗口」那一侧**：库越大，窗口里不相关的内容越多，
插件按需取回就越划算。14 条那个规模上窗口本来就装得下，插件没有优势。

### 一次性成本要摊平多久

大规模下 `derive` 读了一遍全库 = **21,924 tokens**。按每条答案省 52 tokens 算，
需要取回约 **420 条答案**才摊平（4 个问题取回 234 条 ⇒ 还没摊平；
再来一组差不多的问题就回本了）。

### 写入成本：几乎等价

```
经插件（工具调用参数）：69 tokens
直接说在对话里：      33 tokens
⇒ 差的 36 tokens 是 id + 字段，不是正文
```

## 重复任务 / 历史检索：成本的另一种形状

> 探针 `probes/repeat_cost.py` ｜ 逐字输出 `probes/out/repeat_cost.out.txt`
> 140 条笔记，窗口 12 条（359 tokens）

上一组数字每个问题只问一次 —— 只测到「首次取回」。真实使用里还有两种形状：

### A 会话内重复（同一问题问 5 次）

```
WITH     每次重取：1985 × 5 = 9925（答案 12 项）
WITH     答案留在上下文（第 2-5 次不再取回）：1985
WITHOUT  无缓存：359 × 5 = 1795
WITHOUT  有 prompt cache（前缀不变）：359 + 0 × 4 = 359
⇒ 最省的两种：WITH 1985 vs WITHOUT 359 ⇒ **上下文赢**
```

⚠️ **关键条件**：这一局的取回量（1985）**大于**整个窗口（359）。
**取回量 > 窗口量时，重复多少次都救不了插件** —— 因为每一问的取回都比窗口还大。
反过来（答案集很小、窗口很大）才轮到插件赢。

### B 历史检索（问第 1 条，它在窗口外）

```
WITH     2822 tokens｜找到了：True（成本与「多久以前」无关）
WITHOUT  **答不了**（窗口里没有，压缩摘要也没有数值）
```

⇒ 这一局比成本没意义：WITHOUT 的「便宜」是**答不了**的便宜。

### C 跨会话重复（新开一次对话）

```
WITH     1985 tokens｜答案 12 项（库还在，成本不变）
WITHOUT  **从零开始** —— 什么都没存，要人重新贴一遍
```

### 三种形状，三种结论

| 形状 | 谁赢 | 为什么 |
|---|---|---|
| **A 会话内重复** | **上下文**（+ prompt cache） | 前缀不变 ⇒ 缓存命中，边际接近 0；插件每次都要重取 |
| **B 历史检索** | **插件（唯一能做）** | 窗口外的条目，上下文里根本没有 |
| **C 跨会话重复** | **插件（唯一能做）** | 上下文不跨会话，库跨 |

⇒ **不是谁替代谁，是分工**：近期重复用上下文，久远/跨会话用插件。
这条比「插件省不省 token」有用得多 —— 它说的是**什么时候该用哪个**。

## 证不了什么

1. **WITHOUT 是「窗口 + 压缩」模型，不是真模型**。它模拟「记忆有上限、摘要丢精度」，
   **不模拟「模型会不会编造」** —— 后者要接真模型才能测。
2. **字数量不是 token 数**。中文大致 1 字 ≈ 1 token、ASCII ≈ 4 字/token，这里只报字数。
3. **规模小**：14 条笔记、窗口 12 条，都是刻意压小的 —— 关键是**比例**
   （窗口容量 < 笔记总量），不是绝对量。
4. **压缩策略是机械的**（「早前 N 条，数值已略」）—— 真模型的摘要会保留什么，
   取决于它，不由我定。这一趟测的是「压缩必然丢精度」这个结构性后果。
